# P1 管理员商店：模板箱无限库存

Status: ready-for-agent
Type: spec

## Problem Statement

现在的管理员店（第 1 行 `Admin Shop` + 编辑者是 OP）必须往箱子里放货，而且库存是真的会减少的：

- 卖光就要人工补货，公共商店一晚就被买空；
- 进货（玩家卖给它）会把箱子塞满，塞满之后它连"收"都收不了；
- 想换商品得把箱子清空再放新物品。

Java 版 ChestShop 的管理员店是没有库存的概念（`AdminInventory`）：买东西凭空发、卖东西凭空收，箱子只是装饰。

## Solution

**模板箱模式**：管理员店照旧要一块绑定的容器，但那个箱子从"库存"降级为"模板"——

- 箱子里**第一个非空槽位的物品**定义"这家店卖什么"（沿用 §5.3 的商品判据，不做物品 ID 反查），
  这一格叫**样品槽**：**永远不出售、也永远不会被写入**（买入不从它扣，卖出不往它放）；
- 买：凭空发出一份货给玩家，**样品槽数量不变**（永远不会卖光）；
- 卖：玩家交来的货**直接销毁**（不写进任何格子），钱照旧凭空记账——所以也永远"收得下"，
  同时按 `p1-transaction-log` 的约定把销毁的物品写进 `discarded-YYYY-MM-DD.jsonl`（完整 SNBT，见 D3）；
- 第一格以外的格子**一律忽略**：既不当库存、也不装货、也不因为里面放了东西而拒绝交易。
  它们是纯储物/装饰，所以你往第二格随手丢几组东西，这家店的买卖一点不受影响
  （2026-11-01 定：比"第二格起算额外库存"好解释，比"有额外物品就拒绝"不容易踩）；
- 买家看到的库存是**无限**（表单写「库存：无限」而不是编一个数字），
  正文同时写出商品名——买家看牌面第 4 行与箱里那一件就知道自己买/卖的是什么；
- 模板箱空了 → 这家店没有商品，按「暂不可交易」处理（不给买卖按钮，正文说明要放一件样品）。

非管理员店（普通店）行为一个字不改：库存仍然真实增减。

## User Stories

1. 作为 OP，我想开一家永远有货的公共商店，以便不用每天补货。
2. 作为 OP，我想开一家无限收购的商店，以便当玩家的销赃/回收站。
3. 作为 OP，我想在箱子里放一件样品来定"这家店卖什么"，以便不用记物品 ID。
4. 作为 OP，我想把样品换掉就换商品，以便不用清空整箱。
5. 作为 OP，我想模板箱空了就别装成"卖光了"，而是明确说这家店没设商品。
6. 作为玩家，我想在无限库存的店里一次买很多份，以便不用重复点。
7. 作为玩家，我想卖东西给无限收购的店时不被"箱子满了"拒绝。
8. 作为服主，我想普通店的行为完全不变，以便现有商店不受影响。

## Implementation Decisions

### D1 为什么不做"无容器纯牌面"

无容器模式要求从牌面文本反查物品（物品 ID、aux、附魔/耐久/自定义名的稳定表示），等于把 §5.3 的"商品由容器决定"整体推翻，还要额外做：编辑 UI、旧牌迁移、以及在牌面上表示 NBT 的稳定编码。模板箱模式只要在读库存时把"第一个非空槽位"换成"无限"，改动面小得多，而且保留了严格物品匹配。

### D2 无限在纯逻辑层的表示

`ShopInfoData` 现在用 `stockUnits`（可成交份数）表达库存，份数上限另外走 `TradeRequest.goodsUnits` / `roomUnits` 与 `TradePricing::tradeUnits`。无限不用 `INT_MAX` 糊，而是显式一个标志位：

```
struct StockView { std::optional<int> units; bool unlimited; };
```

- `unlimited == true` 时 `units` 必须为空（不能同时有两种真相）；
- `planTrade` 的份数上限计算里，"库存"这一项对无限库存不参与 `min`；
- 表单正文与按钮文案都走同一个格式化函数，避免一处写"无限"、一处写数字。

### D3 卖进管理员店的物品去哪：销毁，但留 NBT 记录

**物品销毁，记录留档**（2026-11-01 定）。销毁的理由三条：

1. 模板箱模式的前提是"箱子只是模板"，往里写会破坏"数量不变"这条最直观的性质；
2. 箱子满了会让这家店连"收"都收不了，与"无限"矛盾；
3. 钱本来就是凭空记的，物品凭空消失是同一种语义（系统账户两侧对称）。

留档的理由一条就够：**销毁是不可逆的，而"这个数据包/附魔书被判为一件普通物品"这种事只能事后查**。

落在哪：`plugins/Shop/logs/discarded-YYYY-MM-DD.jsonl`，一行一条销毁记录，字段为
`ts` / `shop{dim,x,y,z}` / `player{xuid,name}` / `item{id,aux,name,nbt}`，
其中 `nbt` 是 `ItemStack` 的完整 SNBT 字符串（`ItemStack::save` 出来的那份）。
规则细节（压缩、失败处理、与业务流水的关系）全在 `p1-transaction-log` 的 spec D5，这里只约定"必须有"。

这一条要在 DESIGN §7.4 明写，免得以后有人当 bug 修。

### D4 样品槽是"读"出来的，不是"记"下来的

不做任何持久化：每次要用就问一遍容器"第一个非空槽位是什么"。
换商品 = 把第一格换成别的东西（甚至不用清空整箱），下一笔交易立刻按新商品算。
代价是"同一笔交易里商品不能变"——`planTrade` 只读一次，交易过程中换了也按开始那一刻算。

**「第一格」指第一个非空槽位，不是固定的 0 号槽**：箱子里 0 号空、1 号放了钻石，那钻石就是样品槽。
（用户口语里的"第一格"是这个意思；写成固定槽号会在"箱子前面空着"时判成"没有商品"。）

### D5 补偿必须双向且对称

买入失败（背包满 / 钱扣了发不出货）→ 退款；卖出失败（钱记了但没收下货）→ 把物品还给玩家。
因为"写入模板箱"这一步没有了，补偿里少了一次容器回滚，但**发/收货那一步必须真的做完**才允许 `Done`。

## Testing Decisions

**缝是 `planTrade` / `maxTradeUnits`**（`src/shop`，纯逻辑）。`StockView` 就在这一层引入，mod 层只负责「管理员店 → `makeUnlimited()`」这一句翻译。

- **测什么**：无限时库存项不参与 `min`；卖出方向 `roomUnits` 不参与；`goodsUnits`/`roomUnits` 的"<= 0 就拒"在无限时**不触发**；
  其余三个上限（余额、单次上限、收货方空间）在无限下仍然生效；`ShopInfoData` 正文与按钮在无限下的文案；
  模板箱空 → 走 `unavailableReason` 而不是 `NotEnoughGoods`。
- **不测什么**：不在单测里造容器；「交易后第一格逐字段不变」这条要真机（或集成）验，单测只测"模型说无限"。
- **先例**：`tests/shop/TradePlanTest.cpp`（35 个 `TEST_CASE`，含 `maxTradeUnits(100,5,4,0,0)==4` 这种"免费店钱不是限制"的边界断言）、
  `tests/shop/UnitsFormTest.cpp`（上限如何变成表单档位）。

## Out of Scope

- 系统账户作为可查询/可充值的真实账户（另一条 P1）
- 管理员店的表单里选商品
- 税率对管理员店生效（DESIGN §7.4 明确不收）
