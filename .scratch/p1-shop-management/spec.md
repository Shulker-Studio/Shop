# P1 商店管理表单

Status: ready-for-agent
Type: spec

## Problem Statement

店主现在管不了自己的店。P0 只有一个假按钮：点「管理商店」发一句「商店管理功能待实现」。

能改价的路只有一条——**潜行 + 右键**进原版编辑界面，手写四行文本。问题有四个：

1. 触屏（基岩版一半玩家）上"潜行"这个动作很别扭，改一次价要按三个键。
2. 改价必须记格式：`B 10 : S 5`，写错就整块牌失效。
3. 改价时看不到"现在箱里还剩几份""余额能不能付得起"，改完才发现卖不动。
4. 关掉一家店只能拆牌，拆了就没了，重开要重新写牌、重新绑箱子。

## Solution

店主（与 OP）点牌后在表单里拿到「管理商店」，进一张管理表单，能做完三件事：

- **改买入价 / 改卖出价**：分别一个输入框，留空 = 不做这一侧生意；提交后服务器规范化回写牌面（与手写编辑走同一套解析与规范化，不允许出现绕过校验的写牌路径）。
- **改每份件数**：一个输入框，范围 `1..maxShopAmount`。
- **停业 / 恢复营业**：不拆牌、不丢归属、不丢库存。停业期间任何人都不能买卖，非店主的牌面保护照旧。
  牌面上只有机器标记 `:x`（第 3 行宽度不够写中文，见 D1）；玩家看得懂的「暂停营业」出现在**点牌后的表单正文**与交易拒绝文案里。

管理表单只对**店主与 OP** 出现；管理员店只对 OP 出现（§9.2 的 fail-closed 口径不变）。

**判据注意**：不能拿 `ShopFormRole` 推导管理入口——`shopFormRoleOf` 对管理员店恒返回 `Visitor`（那是给买卖按钮用的：管理员店所有人都是买家）。管理入口要单独用 `canManageShop(shopActorOf(记录XUID, 玩家XUID, 是否OP, adminShop))` 判，它已经写着「管理员店只有 OP 是主人」（`src/shop/SignProtection.h`）。

## User Stories

1. 作为店主，我想在表单里改买入价，以便不用潜行、不用记格式。
2. 作为店主，我想在表单里改卖出价或清空它，以便随时改收不收货。
3. 作为店主，我想在表单里改每份件数，以便整箱卖和按个卖之间切换。
4. 作为店主，我想改价时看到当前库存与余额，以便知道改完卖不卖得动。
5. 作为店主，我想停业但保留牌子和库存，以便装修期间不接客。
6. 作为店主，我想恢复营业，以便不用重写牌、不用重新绑箱子。
7. 作为 OP，我想管理别人的店，以便帮玩家救回写坏的店。
8. 作为 OP，我想在管理员店上有管理入口，以便维护公共商店。
9. 作为非店主，我不想看到管理入口，以便不会被误点。

## Implementation Decisions

### D1 停业标记写在价格行末尾

牌子是唯一数据源（ADR-0002），停业状态必须能从牌面读出来，所以不能只存在内存里。

候选与取舍：

| 方案 | 问题 |
| --- | --- |
| 清空价格行 | 第 3 行没有 `B`/`S` → 不再「像商店牌」→ **保护整体失效**（§5.1.1），别人能改牌、能拆箱 |
| 第 1 行加前缀 | 管理员店判据是「第 1 行整串等于 `adminShopName`」，前缀会让管理员店掉回普通店 |
| 第 2 行加标记 | 第 2 行必须是纯整数，加标记等于把牌变非法 |
| 上蜡当"停业" | 上蜡是编辑开关，不影响交易（D29），语义冲突 |

**定为**：价格行末尾追加一个停业段 `:x`，即
```
B 10 : S 5 :x      ← 停业
B 10 : S 5         ← 营业
```

- 价格行解析允许第三段固定 token `x`（大小写不敏感，`: x` 也认，规范化恒输出 `:x`），其余仍按 §5.2 处理。
  实现上不是“认第三段”：因为单侧价格时它是**第二段**（`S 5 :x`）。正确规则是“**先剔掉最后一段若等于 `x`**，剩下的再按原文法解，且至少剩一个价”，`segments.size() > 2` 的检查挪到剔除之后。
- 用短标记是因为牌面第 3 行宽度本来就紧（已经有两个价），`off` 会多吃 2 个字符；`x` 是一个完整段，与 `B`/`S` 同级，不会与 `B 10`/`S 5` 的解析歧义。
- 有 `:x` → 牌仍然「像商店牌」（第 3 行含 `B`/`S`）、归属与保护不变、交易统一拒绝并提示「这家店暂停营业」。
- 管理表单在停业时把「停业」按钮换成「恢复营业」（不会出现两个矛盾按钮）。
- 这就是店主视角的「开店 / 关店」开关：关店 = 停业（牌子和库存都留着、随时能开回来），
  **不是**拆店。想彻底不干了才拆牌（拆了归属与绑定一起没，重开要重新写牌、重新贴箱子）。
- 手写编辑时玩家自己写 `:x` 也认——它就是一个合法的价格行写法，不需要额外权限。

### D2 写牌面走"服务端写入 + 补发"

管理表单改价不是玩家编辑事件，走不到 `PlayerEditSignBeforeEvent`。写入用
`SignBlockActor::setMessageForServerScripingOnly(SignTextSide::Front, text, 店主XUID)`：

- 它同时把 `mLastEditXuid` 写成店主 XUID，**归属不变**（ADR-0005 的真相源不被动摇）。
  > 这一条是**头文件推断**（函数名与三个参数的含义），不是实测结论：票 01 必须真机验一次「OP 代改价后，店主仍是原主」。若它没写 XUID，退路是自己补写 `mLastEditXuid`。
- 写完必须把这一格的 `BlockActorDataPacket` 发出去，否则客户端还画着旧文本——与 `resyncBlockActor` 同一套做法（DESIGN §9.2「客户端预演」）。
- **发谁（2026-11-01 定）**：**整个维度的所有玩家**，不只发给定表单的那个人、也不算距离。
  实现的 helper 放 `src/mod/BlockResync.h`（`resyncBlockActorToDimension`）：`ll::service::getLevel()->forEachPlayer`
  遍历，`player.getDimensionId() == signRegion.getDimensionId()` 就发同一个包。
  理由：`forEachPlayer` 本来就只在同一维度的玩家集合上跑，算距离只是多一遍开销；
  改价是低频操作，几十个包不算事；而漏发会让旁边的人对着旧价格谈生意——这比多发包严重。
  > **实现时同步改 DESIGN**：§9.2「客户端预演」那段现在写的是"只发给动手的那个玩家、不广播"，
  > 那条针对的是**拦截**（拦下来的人自己看就行）；管理表单改价是**写牌**，范围不同，要在 §9.2 分开写。
- **落盘未证实**：26.51.8 的 `BlockActor.h` 里没有 `setChanged`，只有 `virtual onChanged(BlockSource&)`（`SignBlockActor` 重写了它）。`setMessage` 是否自己标脏无从证实，所以「改价当场生效、重启回滚」是真实风险：票 01 要做一次「改价 → 重启 → 看牌」验收，退路是写完后显式调 `onChanged(region)`。

### D3 不做「打开商店箱」按钮（2026-11-01 拍板）

原本想在管理表单里放一个按钮直接开箱补货，**否掉**。

理由：店主本来就能右键那个箱子——`allowOwnerOpenChest` 默认 `true`，`ContainerProtectionListener`
对店主是放行的，被拦的只有非店主。所以这个按钮唯一的价值是"省掉关表单 → 找箱子 → 右键"。

而它的成本是这张票里唯一的技术风险：`Player` 上没有打开容器的公开方法（`openContainer` 不在头文件里），
只剩 `ContainerOpenPacket` 裸包，而裸包会让客户端拿到一个**服务端没登记的窗口**——
玩家放进去的东西会丢。为一个省一次右键的按钮去赌物品丢失，不值得。

补货路径保持原样：关掉表单，右键箱子（店主放行）。

### D4 上蜡不拦管理改价

上蜡是**手写编辑**的闸，针对的是“别人/自己写错格式”这类直接改文本的路径。而且蜡**不可逆**（原版告示牌的蜡去不掉，`DESIGN §9.2` 的「上蜡不可逆」），所以管理表单不只是“另一条路”，它是上过蜡之后**唯一**的改价路径。管理表单是经过完整校验的写牌路径，所以：

- 上了蜡的牌，店主/OP 在管理表单里**可以直接改价、改件数、停业/恢复**；
- 管理表单正文写一句「这块牌上了蜡：手写编辑仍被锁，这里可以直接改」，免得店主以为坏了；
- 牌面防护那几道（非店主、染色、上蜡）一个字不改。

理由：否则店主会被自己的蜡锁死——原版**没有**除蜡手段，改一次价就得拆牌重立（等于关店）。蜡的本来目的只是防误改，不该顺带把手写之外的正常管理路径也堵死。需要同步在 DESIGN §9.2 记这一句（“上蜡只拦手写编辑，不拦管理表单”）。

### D5 停业不能把店主自己锁在外面

`shopFormButtons` 现在有两个分支会互相打架：`Manager` 先返回（不理 `unavailableReason`），非 `Manager` 遇到 `unavailableReason` 非空就返回空。管理员店的 OP 是 `Visitor`，所以一停业就**一个按钮都没有**，永远无法恢复营业（除非拆牌）。

**定为**：把「管理入口」从 `ShopFormRole` 里拆出来，改成 `shopFormButtons(data, role, canManage)`：

- `canManage` 由 `canManageShop(shopActorOf(...))` 直接给（与 Solution 段「判据注意」同一条），管理员店只对 OP 为真；
- `canManage` 为真时**总是**给管理入口（停业时文案变「恢复营业」），与 `unavailableReason` 无关；
- 买卖按钮仍然只看 `role` 与 `unavailableReason`。

### D6 不允许把店改成“不再像商店牌”

两侧价格都清空 → 第 3 行变空 → `looksLikeShopSign` 为假 → **保护整体失效**：牌可以改、箱子可以开可以拆。这是“店主点一下就把箱子敞开给全服”，比停业严重得多。

**定为**：管理表单的改价提交必须至少保留一侧价格；两侧都清空的提交直接拒绝，并提示「至少留一侧价格，否则这块牌就不再是商店牌（箱子会失去保护）」。「想关店」的正解是拆牌，或者停业。

## Testing Decisions

**缝（seam）只有一处，且是纯逻辑层**：新增一个纯函数「当前牌面状态 + 新买入价 + 新卖出价 + 新件数 + 停业位 → 新牌面文本或失败原因」。
所有校验（`S > B`、两侧都空、件数越界、`:x` 的解析与规范化）都在这一处，`src/shop` 里可单测。

- **测什么**：上面那个合成函数（正常、单侧清空、两侧清空、件数越界、`S>B`、带 `:x` 的停业与恢复）；
  `ShopInfoData` 的按钮集合（`canManage` 与 `unavailableReason` 的四种组合）；`parsePriceLine` 对 `:x` 的剥离规则。
- **不测什么**：不给 `SignBlockActor` / `BlockSource` 造 mock——写牌、发包、重启后是否还在，一律真机验（这三件都依赖引擎行为，
  mock 出来只会测到自己写的假设）。
- **先例**：`tests/shop/UnitsFormTest.cpp`（模型 → 文案 → 反解析整条链）、`tests/shop/ShopInfoTest.cpp`（按钮集合）、
  `tests/shop/TradePlanTest.cpp`（上限与拒绝原因的组合断言）。风格是 doctest + 直白中文断言消息。

## Out of Scope

- **打开商店箱按钮**（见 D3：店主右键箱子本来就能开，不值得为省一次右键去碰裸包）
- 转移所有权、员工名单（需要新的持久化载体，另开 spec）
- 改商品（商品由容器第一格决定，换商品 = 换箱子里的物品）
- 改牌面颜色 / 上蜡（P0 已有潜行 + 手持物品的路径，管理表单不重复造）

## Further Notes

- 与 P0 的边界：P0 已有的「潜行 + 右键手写编辑」路径**一个字不改**，管理表单是并列的第二条写入路径，
  两条路共用同一套解析与规范化（否则迟早分叉）。
- 实施顺序建议放在另两份 P1 之前：它最容易见效，而且不改 `TradePlan`（无限库存会大改上限公式，先做那个会让本 spec 的验收基座移动）。
- 三处只能真机验的假设（`setMessageForServerScripingOnly` 的 XUID 写入、落盘标脏、上蜡牌能否被写入）已在
  Implementation Decisions 里逐条标注退路，实现时**不要**为了绕开它们去自造 API。
