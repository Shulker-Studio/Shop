# P0.1 验收观测包

Status: ready-for-agent
Type: spec

## Problem Statement

12 票还剩 116 条手测，而现在的判据基本只有两样：**玩家看到的那句话** 和 **控制台日志**。问题是：

- `latest.log` 不实时刷盘（跑到 13:41 时文件还停在 13:23），"日志里没有这行"根本不能当证据；
- hook 注册只在**失败**时 warn 一次，之后无处可查；而且 `HookSlot::attached` 只代表"挂过了"、返回值也不代表成功；
- 经济后端只在 `ServerStartedEvent` 打一行选型结果，错过就没了。

于是每条验收都要靠猜：是保护没触发、还是触发了没拦住、还是这个模组根本没加载。D2 的 20 个子项（16 种染料 + 7 种斧头）尤其难受。

## Solution

三件小事，只服务手测，不改任何行为：

1. `/shop status`：配置快照、经济后端（配置值 → 实际值）、10 条 hook 的**注册尝试结果与返回码**、版本、调试开关状态。
2. `/shop debug on|off`：打开后，在**结果点**各打一行，固定前缀 `[shop/dbg]`。
3. `/shop last [N]`：内存里最近 32 条交易决策（会覆盖），随时查"刚才玩家被拒的理由"。

## 边界（重要）

- **不改 P0 的定义**：`12-manual-acceptance.md` 与 11 张实现票一行不动。本目录是**并行**的观测工具，不是 P0 的验收项，也不阻塞验收。
- **只观测，不改行为**：不新增/修改任何交易、保护、经济路径的判断。`/shop debug` 关闭时一行都不打。
- **与 P1 交易流水的边界**：`p1-transaction-log` 是**账**（落盘、按天轮转、要能审计、不覆盖）；这里是**排障**（内存、覆盖、重启即失）。两边都要，别合并。
- **只在结果点输出**：决策已经定下来之后打一行，不在中间步骤铺日志——否则补偿路径会产生误导性的中间记录。

## 只记这 5 类事件

| 事件 | 时机 | 关键字段 |
| --- | --- | --- |
| `sign_decision` | 一次牌面点击判定完 | `plan=TakeOver/PassThrough/Block/NotAShopSign`、玩家、坐标、手持物、潜行、是否上蜡 |
| `protection_block` | 保护拦下之后 | 类别（开箱/拆箱/拆牌/拆依附方块）、主体、坐标、原因 |
| `trade_result` | `finishTrade` 拿到结果时 | 方向、份数/件数/金额、结果（ok/fail/confirm/frozen）、原因 |
| `content_block` | 漏斗/投掷器/铜傀儡被拦下 | 类别、坐标、介入点 |
| `economy_resolution` | 后端解析/重解析后 | 配置值 → 实际值、跳过原因 |

一份日志要能直接对上测试单的条目编号，所以字段顺序固定、每行一个事件、不打印完整 NBT。

## 关于 `/ll reload Shop`

运行时的 `unload` + `load` 确实存在（`ll/core/command/ModManage.cpp`），但它会卸载/重载 native DLL、事件监听与 detour hook。**不是切换配置档的正常路径**：

- 正常路径仍是停服重启（配置只在模组 `load` 阶段读一次）；
- reload 只作为**可选的鲁棒性试验**，做的话单独记录结果（是否留下重复 hook、旧监听是否还活着），不作为验收捷径。

## 不做

- 持久化任何观测数据（那是 P1 流水的事）
- 按 tick / 按事件流记录，打印完整 NBT
- 把 `debug` 做成配置项（配置要重启才生效，而调试的价值就是"现在就想看"）
- `/shop economy` 这类只读查询的扩展（`/shop status` 已经覆盖）
