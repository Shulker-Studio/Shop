### 从 03 转来的待验项

- [ ] **在 `PlayerInteractBlockEvent` 里 `cancel()` 是否冀能阻止原版告示牌编辑界面弹出**（DESIGN §14「编辑拦截的用户体验」）。
      验证方式：非店主（或店主）点一块合法商店牌，看是否只弹模组表单、而不会先/同时弹出告示牌编辑 UI。
      Plan B（若取消不够）：用 iListenAttentively 的 `ReceivePacketBeforeEvent` / `SendPacketEvent` 拦 `OpenSignPacket`，从服务端不把包发出去。
- [ ] 看背面时模组不接管：玩家站在商店牌背面右击 → 原版编辑界面照常弹（`getSideFacingPlayer` 的实际返回值与扇区边界）。
- [ ] “可成交份数”与实际库存一致（含双箱 54 格的合并统计、混装箱子只算商品本身）。

### 从 04 转来的待验项

- [ ] **买一次：余额、背包件数、商店箱件数三者一致**（§13 第 21 条）。
      验证方式：先把记分板目标 `money` 建好并给买家 100 分；箱子里放 3 组钻石（64/份、B 10）；点牌 → 购买 → 用 `/scoreboard players list` 看分值变成 90、背包多 64 个、箱子少 64 个。
- [ ] **余额不足 → 提示且三者都不变**（§13 第 22 条）：把买家分值改成 5，买一次，看提示是不是「你的钱不够」，且箱子/背包/分值与操作前完全一致。
- [ ] **背包满 → 提示且三者都不变**（§13 第 24 条）：把背包塞满（只留不出 64 个同种物品的空间），买一次 64/份的商店，看提示与三者的前后一致性。
- [ ] **记分板后端真的能读能写**：交易后分值变化能在 `/scoreboard players list` 里看到；**重启服务器后分值仍在**（记分板落盘），且表单里的「余额」显示的就是它。
- [ ] **`ShopInfoData::unavailableReason` 的实际效果**（§8.5）：店主离线时点牌，正文出现「状态：店主不在线，现在不能交易（当前经济后端不支持离线记账）」且**一个买卖按钮都没有**；把 `economy.backend` 换成支持离线的后端（10 落地后再测）时同一块牌应重新出现按钮。管理员店**不应**被这条挡住。
- [ ] **商店箱 UI 开着时能否看到数量变化**：让店主开着商店箱（07 落地后用 `allowOwnerOpenChest`），另一个玩家买一次，确认箱子里显示的件数立刻跟着变（`Container::removeItem` → `ChestBlockActor::setContainerChanged` 是否真的推送）；看不到就说明交易后要显式刷新容器。
- [ ] **`Player::getInventory()` 的 `add` 与我们的背包容量计算一致**：把背包塞到只剩不足一格的同种空间，买一份，确认走的是「背包放不下」而不是「先扣钱再退款」（若走后者，说明容量算多了，日志里会有一条「写回快照」后的退款提示）。
- [ ] **表单回调线程**：04 起回调一律切到 `ServerThreadExecutor` 再动世界，正确性不再依赖回调线程；但仍要确认回调原本跑在哪个线程（§14 待验），以免将来有人误以为可以在回调里直接改容器。
- [ ] **管理员商店的买入被拒绝**：管理员店点「购买」应得到「管理员商店的交易还没实现」且三者不变（资金端属于 11）。
- [ ] **数量表单的档位与上限一致**：库存只够 2 份时下拉框只出现 `1 份 / 2 份 / 自定义份数`（没有 4 份）；选「自定义」填 3 会被拒并提示「1 到 2 之间」，**不会**悄悄成交 2 份。
- [ ] **`1 / 2 / 4 / 自定义` 四档的总价都对**：牌上写 `64 / B 10`，选 4 份应显示「共 256 个 / $ 40」，成交后余额正好少 40。
- [ ] **创造模式被拦**：创造模式玩家点牌买 → 提示「创造模式不能与商店交易」且三者不变；`ignoreCreativeMode: false` 后同一个人可以买（DESIGN §10.4 / §15）。
- [ ] **份数上限 `maxShopAmount` 生效**：把 `maxShopAmount` 改成 2，牌上仍写 `64`，份数表单最多只给 2 份（这是 DESIGN §10.1 第 3 步的 `min(maxShopAmount, ...)`）。
- [ ] **部分成交先弹确认表单**：库存只够 2 份时选「4 份」，应弹出「这家店现在只够成交 2 份（共 128 个）／实际扣款 $ 20」的确认表单；点确认才成交 2 份、扣 20，点取消什么都不动。
- [ ] **冻结生效**：手工构造一次补偿失败（较难，可临时把记分板目标删掉制造写入失败），确认同一玩家对同一块牌再次提交会被拒「这笔交易已被冻结」，并且日志里有 `fatal`、在线 OP 收到红色提示。
- [ ] **双箱刷新**：双箱两半各放商品，买一次后两半的 UI（店主开着箱子时）都立刻显示新数量。
- [ ] **确认表单的「确认」按钮立刻生效**：库存只够 2 份时选 4 份 → 确认表单 → 马上点确认，应立刻成交（不会被 250ms 提交冷却静默吃掉）。
- [ ] **管理员店不被离线策略误伤**：管理员店即便创建者（OP）不在线，表单正文也不应写「店主不在线」，买卖按钮照常给（点击后得到「管理员商店的交易还没实现」）。

### 从 05 转来的待验项

- [ ] **卖一次：背包件数、余额、商店箱件数三者一致**（§13 第 21 条的镜像）。
      验证方式：牌上写 `64 / B 10 : S 5`，箱里放 3 组钻石，玩家背包带 2 组钻石、记分板 100 分；点「出售」→ 1 份 → 确认；背包少 64 个、分值变 105、箱子多 64 个。
- [ ] **不严格同种被拒**（§13 第 25 条 + §5.3）：拿附魔钻石剑（或改过自定义名的钻石）卖一家收普通钻石的店，应提示「你手里的这种物品与商店收的不一样（附魔、耐久或自定义名对不上）」，背包/余额/箱子都不变。
- [ ] **卖：手里没有这种物品** → 提示「你手里没有这么多」，三者都不变。
- [ ] **卖：店主余额不足**（§13 第 26 条）：把店主分值改成只够 2 份，卖 4 份 → 允许部分成交时应按 2 份成交（收入 = 单价 × 2）；关掉 `allowPartialTransactions` 时应整笔拒绝并提示「店主的钱不够，付不起这一笔」。
- [ ] **卖：商店箱装不下**：把箱子填到只剩不足一份的空间 → 提示「商店箱装不下这些物品」，背包与余额都不变；再试双箱只塞满一半，应成交到两半之和（`mergedSlots` 顺序：先附着那一半）。
- [ ] **卖：双箱部分放入不会留下残局**：让箱子刚好差一格，卖一份 → 应走「钱已退回、背包与箱子回到原样」，聊天里出现「这笔交易没有成交，钱已退回」。
- [ ] **钱已动、货搬失败的补偿**（本票勾选项 5 的真机版）：在份数表单打开后、点确认前，用另一个客户端把要卖的那一份挪走或把箱子塞满 → 提交后应看到退款提示且背包/箱子回到操作前。
- [ ] **补偿失败 → 冻结**（本票勾选项 6 的真机版）：临时删掉记分板目标制造写入失败，确认日志有 `fatal`、在线 OP 收到红字、同一玩家对同一块牌再次提交被拒「这笔交易已被冻结（上一次交易未完成，请联系管理员核对）」。
- [ ] **空箱子（卖光）时点牌**：正文出现「状态：商店箱里没有货，既没东西可卖，也看不出这家店收什么」，**一个买卖按钮都没有**；补货后再点，按钮回来。
- [ ] **卖出的份数表单**：上限 = `maxShopAmount`、你手里的份数、箱子还能装的份数、店主余额四者取最小；每档金额与实际收入一致；「你的余额」显示的是买家自己的分值。
- [ ] **卖出确认表单**：库存/余额变化后份数缩水时，正文应是「这一笔现在只成交得了 N 份」+「实际收款」，点确认才成交、点取消什么都不动。
- [ ] **免费店（`S 0`）**：一份 0 元的收购店，玩家卖货时不应因为「读不到账户余额」被拒；成交后聊天里不出现「收入」那一句。

### 从 06 转来的待验项

- [ ] **取消是否挡得住染色/墨囊/上蜡/除蜡**（§13 第 15～18 条的真机版）：
      非店主手持红染料 / 墨囊 / 荧光墨囊 / 蜜蜡点商店牌 → 收到「只有店主（或 OP）能…」的提示，
      且牌子的颜色、样式、上蜡状态一个都没变；再用斧头点已上蜡的牌 → 除不掉。
      这是 `PlayerInteractBlockEvent` 的 `cancel()` 能否阻止 `SignBlockActor` 改动的问题，
      与「取消能否阻止开牌/开箱」是同一条风险。
      Plan B（若取消挡不住）：染色/上蜡没有可拦截的提交事件，只能改为事后检测 + 回写（`setMessageForServerScripingOnly`）。
- [ ] **店主的同四类操作真的生效**（§13 第 19 条）：店主/OP 手持红染料 → 字变色；墨囊 → 发光字取消；
      荧光墨囊 → 发光；蜜蜡 → 上蜡；斧头 → 除蜡。这条验的是「不取消、交回原版」是否走通。
- [ ] **潜行 + 右键是否真的弹原版编辑界面**：店主潜行右键自己商店牌的正脸 → 原版告示牌编辑界面弹出且能保存；
      非店主潜行右键 → 仍然只出商店表单（不弹编辑界面）。
      若基岩版潜行会挡掉方块交互，Plan B：换成「手持空手 + 潜行仍弹表单」之外的入口（例如管理表单里的「编辑牌面」按钮）。
- [ ] **上蜡后的编辑体验**（§13 第 20/20b 条）：店主潜行右键已上蜡的牌 → 我方提示「这块商店牌上了蜡，先拿斧头除蜡才能改」；
      用斧头除蜡后再潜行右键 → 能进编辑界面并保存。同时确认原版自己也会拒绝（`FailWaxedSign`），两条不打架。
- [ ] **`SignBlockActor::mIsWaxed` 的实际取值**：新放的牌子是 false；刷蜜蜡后是 true；
      斧头除蜡后回到 false（重启服务器后再点一次确认持久化）。它决定验收第 7 条与提交阶段的第二道闸。
- [ ] **`ItemStack::getTypeName()` 的返回值形态**：确认它给的是 `minecraft:red_dye` 这种类型名；
      然后逐一点过 16 种染料、墨囊、荧光墨囊、蜜蜡与 7 种斧头，确认店主那一侧都被放行（分类器没漏判）。
- [ ] **`mLastEditXuid` 是否被包路径写入**（ADR-0005 的落地核心）：新牌第一次写成商店后，重启再看店主是不是自己。
      再让 OP 代改一次别人的商店 → 归属与牌面第 1 行都不变（这条同时验「引擎写了我们纠回来」「没写我们补上」两种情形）。
- [ ] **归属不会跟着编辑者走**（§13 20d/20e）：A 先在一块牌上写普通公告、B 再把它改成合法商店 → 店主是 **B**
      （归属写给「把这块牌变成商店」的人）；OP 代改一次别人的商店 → 店主与第 1 行都不变。
      注意：店主把商店改回普通文本等于**关店但不拆牌**，这时 B 把它重写成商店，店主就是 B（不是 A）。
- [ ] **拆掉商店箱之后**（§13 20f）：非店主改不了牌面、上不了蜡；店主与 OP 点牌仍能进原版编辑界面（店坏了要能修回来），
      非店主点牌只收到「这家店暂时用不了（商店箱不在了）」。
- [ ] **提交阶段的兜底本身**：让非店主拿到原版编辑界面（拆掉商店箱后由店主先点一次、或另一个模组发编辑包），
      提交后应收到「这块商店牌是 X 的，只有店主（或 OP）能改」，且牌面一个字没变；同样位置店主提交能保存。
- [ ] **上蜡后的商店照常买卖**（§13 第 20 条后半）：把商店牌上蜡，另一个玩家点牌 → 表单照弹、买卖照常成交，
      只是谁都改不了牌面。
- [ ] **背面不是后门**（§13 20c）：非店主站在商店牌背面，手持蜜蜡点牌 → 被拦、牌子不上蜡；
      手持染料点背面 → 被拦。空手点背面 → 原版编辑界面照弹（背面照常可以写）。
- [ ] **非店主拿斧头点没上蜡的牌**（§13 20g）：不弹「除蜡」相关提示，只弹商店表单，牌子无变化。
