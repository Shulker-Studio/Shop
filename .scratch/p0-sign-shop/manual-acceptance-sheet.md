## 0.0 先把服务器跑起来（一次性，约 20 分钟）

### 0.0.1 版本三件套必须对得上

| 组件 | 本模组的要求 | 怎么确认 |
| --- | --- | --- |
| BDS + LeviLamina | **LL `26.51.x`**（构建基线 `26.51.8`）。LL 26.x 小版本之间不保证 ABI 兼容，版本不一致时先对齐再测，别把“加载/符号失败”当成商店的 bug | `plugins/LeviLamina/manifest.json` 里的 `"version"` |
| iListenAttentively | **`>= 0.17.0`**，且必须是**已安装**（不只是有文件） | `plugins/iListenAttentively/iListenAttentively.dll` 存在 |
| Shop | 本次构建产物 | `plugins/Shop/Shop.dll` + `manifest.json` |

### 0.0.2 部署 Shop

```bash
xmake build Shop                      # 产物在 bin/Shop/：Shop.dll、Shop.pdb、manifest.json
cp bin/Shop/* <服务器根>/plugins/Shop/
```

`manifest.json` 里必须有这一段（**没有就会重现 `0x0000007E`**）：

```json
"dependencies": [ { "name": "iListenAttentively" } ]
```

### 0.0.3 装 iListenAttentively（缺了就是加载失败，不是“少功能”）

```bash
cd <服务器根>
lip install github.com/LiteLDev/iListenAttentively     # 或手动解压 release zip 成 plugins/iListenAttentively/
ls plugins/iListenAttentively/iListenAttentively.dll
```

- iLA 是**被动库**（manifest 里 `passive: true`）：没有模组声明依赖它时 LeviLamina 不会加载它。现在 Shop 声明了，顺序就变成「先 iLA、后 Shop」。
- 它的 `manifest.json` 里 `"name"` 必须**等于目录名** `iListenAttentively`，不一致 LL 会跳过（`Mod name ... do not match folder ...`）。

| 日志 | 含义 |
| --- | --- |
| `std::system_error … 0x0000007E` / `missing module: iListenAttentively.dll` | manifest 缺 `dependencies`，或 iLA 目录名/manifest 不匹配 |
| `Missing dependency iListenAttentively` | 依赖声明生效了，但 `plugins/iListenAttentively/` 没被认出来 |
| `config.json 非法：…` / `配置不可用，Shop 拒绝加载` | 配置值越界（见 0.4 的 K9） |
| `config.json 缺少 version 或为空，已按默认值补齐` | 只是提示：手写的配置没有 `"version": 1`，已回写完整文件，不影响测试 |

### 0.0.5 客户端与账号（这是最容易卡住的一步）

- 需要 **2 个微软账号**（`A`、`B`）。同一个账号不能同时在线两份（后进的会把先进踢掉）。
- 同机测试：Windows 客户端连 `127.0.0.1:19132`；手机/另一台电脑连服务器**局域网 IP**`:19132`（UDP）。
- `server.properties`：`server-port=19132`，`allow-list=false`（或把两个号加进 allowlist），`online-mode` 基岩版没有这个键，别去改。

  这台服是 `allow-list=true`，当前只有 `lwenk` 一个（见 0.0.7）。第二个号进服前先在控制台发
  `allowlist add <名字>`（名字要跟 Xbox 显示名一致），或把 `allow-list` 改 `false`。
- 进服后：`CON` 发 `/op A`，`/gamemode creative A`、`/gamemode creative B`。
- **只有 1 个账号时能测什么**：保护类（D4 全部）、牌面防护大部分（D2，店主视角）、创建类（D1）、边界类（D5）都可以「A + CON」或「A + B 互相当访客」勉强跑；但**必须 2 人**的有：A 组全部（管理员店买卖要有人收钱）、B 组全部（买卖双方余额同时要看）、D3 的「不能跟自己交易」以外的双向余额核对。

### 0.8 只读检查发现的三处口径问题（执行前先知道，别记成“实现坏了”）

1. **B9 / `maxShopAmount` 与"牌上仍写 64"冲突**。
   `ShopSign::parseAmountLine` 把"一份的件数 > `maxShopAmount`"判为非法，所以把 `maxShopAmount` 改成 2 之后，
   **已经有 `64` 的商店牌会整块变成非法牌**（点牌得到"这家商店已经不在了"/牌面不再被当作有效商店），
   而不是"份数表单最多给 2 份"。两条口径都成立、但不能用同一次试验同时验：
   - 验"创建期上限"：`K3` 下新建一块写 `64` 的牌 → 应被拒（"一份的件数要写 1 到 2 之间的整数"）；
   - 验"份数上限"：`K3` 下新建一块写 `1` 的牌，箱里放 ≥ 4 个 → 份数表单最多 2 份。
   想验"老牌遇到调小的上限"就按实测现象登记（这是配置收紧的语义问题，属设计侧判断）。
2. **第 4 行"超宽截断"没有实现**。`formatShopSign` 原样写入 `product->getName()`，代码里没有截断逻辑
   （`DESIGN §5.3` 写的是"超宽截断"）。所以 C4 请按实测登记：牌面 4 行是否被引擎渲染截断、表单里是否全名。
3. **`economy.backend: "null"` 时 `supportsSystemAccount()` 为假**，A7 期待的是
   "当前经济后端没有系统账户，管理员商店现在不能交易…"，**不是**"服务器没有可用的经济后端"。
   两者分别属于“后端声明不了系统账户”与“一家后端都没有”，A7 会各跑一次。

### B21 卖出时的份数上限 + 免费店（拆成两小步，分不清就照这个做）

卖出是「店主付钱买你的货」，所以上限由**四个数里最小的那个**决定：

| 上限来源 | 怎么算 | 通常会不会成为瓶颈 |
| --- | --- | --- |
| `maxShopAmount` | 配置，默认 3456 | 基本不会 |
| **你手里有几份** | 背包里这种物品的数量 ÷ 每份件数 | 常见 |
| **商店箱还能装几份** | 箱里空位 ÷ 每份件数 | 常见 |
| **店主付得起几份** | 店主余额 ÷ 单价（收税时还要多留税钱） | 常见 |

#### B21a 上限被「店主余额」压住（最快能验的一个）

  （店主只剩 5 元，只付得起 1 份）。
- **操作**：B 点 `S1` → 出售 → 看表单正文与档位。
- **预期**：上限显示 **1 份**（不是 3 份）；档位里「2 份 / 4 份」都不出现；正文里
  「你手里有 3 份 / 商店箱还能装 N 份 / 店主余额 5 / 你的余额 …」几行都在。
  选 1 份能成交（店主 -5、B +5）；想卖 2 份提交不出去（输入框会报「要在 1 到 1 之间」）。
- **失败看**：上限是多少就看 `unitsFormContent` 里那行「（卖出的上限）…」与档位列表。

#### B21b 上限被「箱空间」压住（可选，想省时间就跳过）

- **准备**：把 `S1` 的箱子塞到只剩 1 格空位（只剩 64 件的空间）；B 手里有 3 份。

#### B21c 免费店 `S 0`（这一条独立，别和上面混）

- **准备**：`S5` 是 `64 / S 0`（只收购、价格为 0，即「免费收」）。B 拿 64 个钻石点它 → 出售。

- **预期**：**能成交**（货进箱子、B 背包 -64）；聊天里**不出现**「收入 $0」这类话（0 元不动账，

- **为什么值得测**：这是唯一一个「店主一分钱都不出」的卖出场景，最容易在
