# 破坏保护做到方块级，故意偏离 Java 版

爆炸、活塞推动、凋灵破坏、火焰对商店箱的影响，用方块级手段处理：从爆炸的方块列表里剔除商店箱、让活塞推动在商店箱处返回失败、让凋灵的破坏在商店箱前提前返回（落点后来改过，见文末「修订」）。**Java 版 ChestShop-3 不是这么做的**——它一旦发现爆炸/推动/燃烧列表里含有受保护的箱子，就直接取消整个事件，于是玩家看到的是"附近有商店，整场爆炸哑火"。

这一条是刻意偏离：基岩版的爆炸与活塞范围大、玩家对"爆炸莫名其妙无效"的容忍度低，整场取消会被当成服务器 bug。代价是要自己维护四个方块级 hook，并跟随 LeviLamina 内部符号漂移。ChestLock 的同一组 hook 已在旧版本验证过符号存在且语义正确，因此这不是从零起步的风险。

## 修订（08 落地时）

原文把凋灵那一条写成「让凋灵的破坏在商店箱前提前返回」。落地时发现这个描述与决策本身矛盾：26.51.8 的
`WitherBoss::_destroyBlocks(Level&, AABB const&, BlockSource&, int, WitherAttackType)` 一次只拿到整个
`AABB`，提前返回等于取消那一次破坏的全部方块——旁边的一块也不掉，正是本 ADR 要避免的「整场哑火」。

所以落点改成：`_destroyBlocks` 只置一个「凋灵正在破坏」的线程局部标志后照常放行原版，
由 `Level::destroyBlock` 在标志期内对商店方块逐格返回 `false`。**决策不变**（方块级，而不是取消整场），
变的只是 hook 落在哪一层。标志只在这一次凋灵破坏期间为真，因此不影响爆炸（H3a 自己剔除方块列表）、
玩家拆除与所有权判定（07）、以及放行后我们主动打掉商店牌的那次 `Level::destroyBlock`。

代价是多了一条对引擎路径的假设：凋灵销毁方块必须经过 `Level::destroyBlock`。这一条无法单测，
只能真机验收（`.scratch/p0-sign-shop/issues/12-manual-acceptance.md` 的「从 08 转来的待验项」）；
若真机发现守卫一次都没命中，退路是回到提前返回，并接受「凋灵范围内旁的方块不被破坏」这个明确的行为偏离。
